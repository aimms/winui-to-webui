# Upgrading AIMMS WinUI applications to AIMMS WebUI applications

AIMMS WinUI applications should be upgraded to AIMMS WebUI applications such that the learning curve of end-users of the upgraded application is minimal.

Reason for urgency on this application: AIMMS Development puts a cap on the lifetime of AIMMS WinUI applications.

## Background/History

AIMMS has two UI builders.
WinUI is the original, Windows-only UI from the 1990s that draws directly on the desktop.
WebUI is the modern browser-based UI (2016+) that runs in Chrome and other modern browsers.

### Common

Common to these UI builders is that the UI is built on a point and click basis and that the specifications of the UI are mostly text based.

### Differences

In the details, there are several differences:

1. The WinUI is XML based, the WebUI is .json based. (with Python, no problem)
2. The WinUI has positions for every object, the WebUI has a layout, and within that layout, Widgets are placed. (arbitrary choice made for now)
3. The WinUI offers expressions and action sequences; the WebUI requires single identifiers. (Handled via generated interface identifiers)

### Upgrade problems

1. WinUI Pivot tables provide their pivoting information via binary files; the pivoting chosen in the WebUI needs to be adapted accordingly manually.
2. The WinUI offers commands from AIMMS Developer. These commands are not accessible in the WebUI.

## Project purpose

Many AIMMS WinUI apps are business-critical and contain dozens or even hundreds of pages.
Not only is there value in the project itself, but also value in the knowledge of end-users using these applications.
Manually rebuilding all these pages in WebUI is slow and error-prone.
In addition, a totally new design will also impact the learning curve of end-users for the upgraded application.

This project delivers a conversion tool that reuses the overlap between WinUI and WebUI to generate a working WebUI scaffold automatically.

## Current State

- Working WinUI to WebUI converter driven by `winui_to_webui.process_aimms_app()` (`winui_to_webui.py`): copies helper libs, opens the AIMMS model, generates a runtime library, walks `PageManager.xml`, and writes `WebUI/webui.json` per component.
- Two entry points: GUI/CLI in `main.py`; CLI also used by automation and tests.
- Conversion logic covers pages, text/image/iframe/button widgets, tables/pivots, selection boxes, and charts; handles identifier slicing/pivoting and title extraction (`web_page.py`, `win_page.py`, `win_object_tools.py`).
- 21 curated examples (`examples/w2w0000` ... `w2w0020`) with expected outputs; regression scripts in `scripts/run_example.py` and `scripts/run_all_examples.ps1`. Pytest wrapper `test_winui_to_webui.py` runs all examples end-to-end.

## Evidence / How to Demo

- Manual: `uv run main.py` ? pick folder/name, or `uv run main.py "..\\examples\\w2w0004\\work" w2w0004`.
- Batch: `./scripts/run_all_examples.ps1` (logs to `logs/<example>-timestamp.txt`); add `-Examples w2w0001,w2w0004` to filter, `-StopOnFailure` to fail fast.
- Tests: `pytest -vv --maxfail=1 test_winui_to_webui.py` compares generated WebUI against expected for every example.

## Known Gaps / Risks

- Several WinUI Object types still need conversion to corresponding WebUI widget types; most notably Tabbed pages.
- Widget support for read only, widget visibility, widget titles, number of decimals per identifier.
- Conversion log readability - clearly needs feedback and work on that.
- Data coloring / legends
- Widget placement / WebUI page layout is trivial/
- w2w_gui doesn't look good (to put it politly)

## Risks

- Type hints rely on generated stubs; ensure `modeledit_aimmspy*.pyi` stays in sync with AIMMS Python bindings.
